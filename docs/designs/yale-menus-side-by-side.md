# Design: Yale Menus, three dining halls side by side

Generated by /office-hours on 2026-10-17
Branch: main
Repo: daniel-lu32/yale-menus
Status: APPROVED
Mode: Builder

## Problem Statement
Picking between Grace Hopper, Silliman and Branford dining halls means clicking through three separate Nutrislice pages, one meal at a time. Goal: one page that shows all three colleges' menus side by side so the choice takes seconds, with essentially zero ongoing compute cost on the user's laptop.

## What Makes This Cool
It turns a menu viewer into a decision tool: open it, see the current meal for all three colleges at once, and instantly spot the dish only one college is serving today. That dish is usually what decides where you eat.

## Constraints
- Personal tool (user plus friends). No accounts, no database, no backend server.
- Must not run anything on the laptop day to day. Published via GitHub Pages; local preview only during development.
- Data source: Nutrislice public JSON API (verified live on 2026-10-17):
  - School list: `https://yalehospitality.api.nutrislice.com/menu/api/schools/`
  - Weekly menu: `https://yalehospitality.api.nutrislice.com/menu/api/weeks/school/{slug}/menu-type/{meal}/{YYYY}/{MM}/{DD}/`
  - Slugs: `hopper-college`, `silliman-college`, `branford-college`. Meals: `breakfast`, `lunch`, `dinner`.
  - The weekly endpoint returns Sunday through Saturday. Items carry `is_section_title`, `text`, `food.name` and `food.icons.food_icons[].name` (Vegan, Gluten Friendly, Pork, Soy and so on).
  - Weekend breakfast arrays come back empty (brunch appears to be served under lunch).
- The API sends no CORS headers, so a browser page cannot call it directly. Data must be fetched server-side ahead of time (here, in GitHub Actions).

## Premises
1. Use the Nutrislice JSON API rather than scraping HTML. Agreed.
2. Show breakfast, lunch and dinner for all three colleges in side-by-side columns, defaulting to today and the current meal, with a date picker. Agreed.
3. Being a few hours stale is acceptable; no accounts or database. Agreed.
4. Zero processes on the laptop beats a lightweight local process; publishing to GitHub Pages is fine. The user first objected ("must be local only"), then reversed: "I'd like for the tool to be published to github pages." Final: agreed.

## Approaches Considered
### Approach A: Snapshot page, minimal
A cron workflow and a Python script write `menus.json`; a static page renders three columns. Not chosen: it lists the food but does nothing to help you choose.
### Approach B: Snapshot page plus filters and highlights (chosen)
See Recommended Approach.
### Approach C: Live page via a Cloudflare Worker CORS proxy
Not chosen: it needs a second account and deploy, and adds a runtime failure point for little benefit, since menus rarely change during the day.

## Recommended Approach
**B. Snapshot generated by GitHub Actions, static front end on GitHub Pages.**

Architecture:
- `scripts/fetch_menus.py`: standard library only (`urllib`, `json`, `zoneinfo`). For each college × meal, fetch the current week and the next week (so Saturday can still look ahead), normalize the data and write `site/data/menus.json`:
  ```json
  {
    "generated_at": "2026-10-17T23:00:00-04:00",
    "colleges": [{"slug": "hopper-college", "name": "Grace Hopper"}, ...],
    "days": {
      "2026-10-17": {
        "dinner": {
          "hopper-college": {
            "status": "ok",
            "sections": [
              {"section": "DINNER", "items": [{"name": "General Tso's Chicken", "tags": ["Wheat","Soy","Sesame","Gluten"]}]}
            ]
          },
          "silliman-college": {
            "status": "ok",
            "stale_from": "2026-10-17T14:02:00-04:00",
            "sections": [ ... ]
          },
          "branford-college": {"status": "empty", "sections": []}
        }
      }
    }
  }
  ```
  The college list lives in one `COLLEGES` constant at the top of the script, so adding or swapping a college is a one-line change.
  - **Dates:** the script works out "today" and the current Sunday-to-Saturday week in America/New_York (`zoneinfo`), never in the runner's UTC, so a run at 22:00 UTC on Saturday still counts as Saturday locally.
  - **HTTP (eng review C3):** `urllib.request` with a 15 s timeout per request, up to 3 attempts with 2 s then 4 s backoff, requests run one after another.
  - **Previous file (eng review C4):** if downloading the deployed `menus.json` fails, returns 404 or doesn't parse into the current format, treat it as no previous data.
  - **Status per college and meal:** each `days[date][meal][slug]` entry is `{"status": "ok" | "empty" | "error", "sections": [...]}`. `ok` means items came back. `empty` means the API answered with no items, so no menu is posted. `error` means the request failed after retries.
  - **Partial failure keeps the last good data:** before writing, the script downloads the currently deployed `menus.json` from the Pages URL. For any college and meal that comes back `error`, it carries the previous `ok` entry forward, marked with `"stale_from"`. That value is the time the data was actually fetched: if the previous entry already has a `stale_from`, it is kept as is; otherwise it is set to the previous file's `generated_at`. This way the "from <time>" note stays accurate across several failed runs in a row. If there was no previous good entry, the status stays `error`. If every fetch fails, the script writes the previously deployed `menus.json` back unchanged (its `generated_at` is kept, so the stale banner still fires), prints a `::warning::` annotation and the site still deploys, so front-end pushes go live during a Nutrislice outage. Only when there is no previous file (first deploy) does it exit non-zero and skip deploying (eng review A1, D3).
- `site/index.html`, `site/app.js`, `site/style.css`: vanilla HTML, CSS and JS, no build step.
  - The header shows the date picker (the dates available in the JSON), meal tabs (Breakfast, Lunch, Dinner), and a "last updated" stamp from `generated_at`.
  - **Default date:** today in America/New_York (`Intl.DateTimeFormat` with `timeZone: "America/New_York"`), not the device's local zone. If today is missing from `menus.json`, choose the nearest available date and show the stale banner.
  - **Default meal:** set by time of day in America/New_York: before 10:30 breakfast, before 14:00 lunch, otherwise dinner. If that meal's entries for the day are all `empty` (for example weekend breakfast), move on to the next meal that has data.
  - **Clarifications (eng review C5):** a meal "has data" when at least one college's entry is `ok`; if no later meal qualifies, keep the time-based meal and show its empty/error states. Every chip in the fixed lists always appears, so saved filters always match a visible chip.
  - Three columns on desktop. On phones, one column at a time with swipeable or tabbed college headers, because a phone in the dining hall line is the main use case.
  - **Diet filter chips.** Tags fall into two fixed groups, based on tags actually seen in the API for the week of 2026-10-11:
    - *"Is" tags:* Vegan, Vegetarian, Gluten Friendly, 9 In Mind. A chip labeled with the tag matches items that have it.
    - *"Contains" tags:* Gluten, Milk, Wheat, Soy, Sesame, Eggs, Coconut, Pork, Alcohol, Fish, Shellfish, Peanuts, Tree Nuts (the last two pre-added; eng review C2, D6). Unrecognized tags are written to `menus.json` as `unknown_tags` and reported as a `::warning::` in the Actions run. A chip labeled "No <tag>" matches items that do not have it.
    - A tag that isn't in either list is shown on the item but gets no chip until it's added to the right list.
    - Selecting several chips combines them with AND: an item must meet every selected constraint, which is the safe reading for dietary restrictions.
    - Items that match stay in full color and the rest are dimmed, not hidden, so the columns stay comparable.
  - **"Only here" badge:** computed only among colleges whose entry for the selected date and meal is `ok` (including carried-forward stale data). It needs at least two such colleges; with fewer, no badges appear and the header says "Comparing N of 3 colleges". A dish gets the badge when its normalized name appears at exactly one of the compared colleges. `normalizeName()` lowercases, trims, applies NFKD and drops accents, turns "&" into "and", strips punctuation and collapses whitespace; display names stay unchanged (eng review C1, D5).
  - **Status display:** `empty` shows "No menu posted". `error` shows "Couldn't load this menu" with a link to the official Nutrislice page. Carried-forward data shows a small "from <time>" note.
  - **Stale banner:** appears when `generated_at` is more than 16 hours old. The longest gap in the schedule is 12 hours overnight (22:00 to 10:00 UTC), so the extra 4 hours covers normal GitHub cron delays and avoids a false alarm every morning.
  - The selected filters are remembered in `localStorage` (wrapped in try/catch).
- **All-day menus (eng review S1, D2):** the script also fetches `salad-bar` and `daily-offerings` for each college (30 requests per run). They are stored under `days[date]["salad-bar"][slug]` and `days[date]["daily-offerings"][slug]` with the same status object (built as separate keys so carry-forward works per menu) and rendered as a collapsed "All day" block (soups, bowls, salad bar, desserts) under each college column. Diet chips apply; "Only here" badges do not.
- `.github/workflows/update.yml`:
  - `schedule: cron: "0 10,14,18,22 * * *"` (UTC: 6am, 10am, 2pm and 6pm Eastern during EDT, an hour earlier during EST), plus `workflow_dispatch` and `push` to main.
  - `permissions: {contents: read, pages: write, id-token: write}`, `environment: github-pages`, `concurrency: {group: pages, cancel-in-progress: false}` (required by deploy-pages; eng review A3).
  - Steps: checkout, set up Python 3.12, run the script, upload `site/` with `actions/upload-pages-artifact`, deploy with `actions/deploy-pages`. Deploying the artifact directly means data snapshots are not committed to the repo, so history stays clean.
  - Keep-alive (eng review A2, D4): `.github/workflows/keepalive.yml` runs weekly (Mondays; changed from monthly during the build, because a monthly check with a 45-day threshold can land after day 60); if the last commit is older than 45 days it pushes an empty `chore: keepalive` commit with the built-in `GITHUB_TOKEN` (`permissions: contents: write`). Note it in the README.
- Local preview: `python3 scripts/fetch_menus.py && python3 -m http.server -d site 8000`. This runs only while developing.
